# modxMCP 2.0 — спецификация

Статус: черновик на утверждение. Разделы пронумерованы, чтобы их можно было утверждать и
править по одному. Открытые вопросы собраны в разделе 16.

Исходные решения владельца: совместимость с 1.x не нужна; MODX 3 не нужен (цель — MODX 2.8.x,
PHP 7.4, по возможности PHP 8.x); работа ведётся сразу на боевом сайте, отдельного стенда для
контента нет; перенос изменений между сайтами не нужен.

## 1. Цели

1. **Безопасность работы на живом сайте.** Любое изменение, сделанное через MCP, можно
   посмотреть и откатить; опасный код не сохраняется; результат проверяется сразу.
2. **Малый расход контекста.** Около 40 инструментов вместо 181, компактные ответы.
3. **Один источник правды.** Инструменты, их схемы и эффекты описаны на сервере (PHP).
   Клиент — тонкий прокси и не меняется от релиза к релизу.
4. **Единый контракт.** Все записи ведут себя одинаково: ревизии, пробный запуск, журнал,
   защита от повторного выполнения, одинаковый формат ответа.

5. **Совместная работа с людьми.** Программист или менеджер может править сайт в админке
   одновременно с ИИ. Их правки попадают в тот же журнал, ИИ о них узнаёт и не затирает
   молча (раздел 8.10).

Не цели: совместимость с клиентами и именами инструментов 1.x, поддержка MODX 3, синхронизация
между сайтами.

Утверждено владельцем: обобщённые имена инструментов с параметром `kind`; удаление
инструментов VersionX; учёт ручных правок в админке.

## 2. Архитектура

```
MCP-клиент (Claude Code, Cursor…)
   │ stdio
Node-прокси (client/)            — манифест с сайта, проверка аргументов, HTTP
   │ HTTPS, POST JSON, токен в заголовке
api.php                          — HTTPS/IP, токен → область доступа, конверт, request_id
   │
Ядро (core/components/modxmcp/src/)
   Реестр действий → Действие (схема, эффект, область, группа)
   Конвейер записи → блокировка → ревизия → проверка кода → снимок «до»
                   → выполнение → снимок «после» → кэш → аудит
   Реестр видов объектов (kind) → чтение/запись/снимок/восстановление
   Журнал (таблицы + хранилище содержимого)
```

### 2.1. Структура PHP

16 трейтов с общей приватной областью заменяются классами с автозагрузкой в пространстве
имён `ModxMCP\`:

```
src/
  Kernel.php                 разбор запроса, диспетчеризация, конверт ответа
  Auth/                      TokenStore, Scope, Security (HTTPS, IP — перенос из 1.10)
  Action/                    по классу на инструмент; базовые ReadAction, WriteAction
  Kind/                      по классу на вид объекта; KindRegistry
  Write/                     WritePipeline, Lock, Revision, StaticFileStager
  Journal/                   Journal, Changeset, Snapshot, BlobStore, Undo
  Lint/                      PhpLint (позже FenomLint)
  Verify/                    Runner, PageCheck, LogReader (перенос из 1.10)
  Request/                   RequestStore (перенос из 1.10)
  Integration/               VirtualPage, MiniShop2, Migx — только объявления видов
```

Действие объявляет всё о себе само: имя, входную и выходную схему, эффект, требуемую область
доступа, группу, обратимость. Манифест (раздел 4) собирается из этих объявлений.

Чистая логика (Security, Revision, Snapshot, PhpLint, RequestStore, сборка манифеста) не
зависит от MODX и покрывается автономными тестами в CI. Тесты, требующие сайта, не вводятся.

### 3.1. Виды объектов (`kind`)

Вид — это описание того, как читать, писать, снимать и восстанавливать один тип объектов.
Новый вид добавляется одним классом и не требует нового инструмента.

| Область | Виды |
|---|---|
| Элементы | `chunk`, `snippet`, `template`, `plugin`, `tv`, `category`, `property_set` |
| Контент | `resource` (значения TV — поле `tvs` самого ресурса) |
| Настройки | `system_setting`, `context`, `context_setting`, `namespace`, `lexicon_entry` |
| Файлы | `media_source` |
| Доступ | `user`, `user_group`, `group_member`, `role`, `access_policy`, `policy_template`, `resource_group`, `context_access`, `resourcegroup_access` |
| Пакеты | `package`, `provider` |
| VirtualPage | `vp_event`, `vp_handler`, `vp_route` |
| miniShop2 | `ms2_option`, `ms2_link_type`, `ms2_product_link`, `ms2_category`, `ms2_order` |
| MIGX | `migx_config` |

Виды интеграций видны только если дополнение установлено и группа не отключена — как в 1.10.

### 3.2. Особые операции (`invoke`)

То, что не укладывается в list/get/create/update/delete, объявляется как операция вида и
вызывается через `invoke {kind, op, …}`. Примеры: `tv` → `suggest_type`, `list_input_types`;
`property_set` → `assign`, `unassign`; `vp_route` → `resolve`; `ms2_option` →
`assign_to_category`; `resource` → `create_draft`, `apply_draft` (раздел 10); `chunk`,
`snippet`, `template`, `plugin` → `make_static`.

Схема аргументов каждой операции отдаётся в `describe`. Операции-записи идут через конвейер.

## 4. Манифест и клиент

Сервер отдаёт манифест действием `manifest`: для каждого инструмента — имя, описание,
входная и выходная схема, эффект (`read_only`, `destructive`, `reversible`, `open_world`),
требуемая область доступа, группа; плюс версия сервера и хеш манифеста. Манифест уже
отфильтрован под токен: недоступные токену инструменты в него не попадают.

Клиент (`client/`, Node ≥ 18):

- при `tools/list` запрашивает манифест и отдаёт его как список инструментов MCP, переводя
  эффекты в аннотации;
- проверяет аргументы по входной схеме до отправки, результат — по выходной;
- для записей создаёт `request_id`, если модель не передала `_request_id`;
- запоминает ревизию каждого объекта, который модель прочитала или изменила в этой сессии,
  и сам подставляет её как `expected_revision`, если модель его не передала (раздел 8.10);
- создаёт идентификатор сессии при запуске и передаёт его в каждом запросе;
- при изменении хеша манифеста в ответе сервера отправляет `tools/list_changed`;
- отдаёт встроенную справку как ресурсы MCP и готовые сценарии как prompts;
- если сайт недоступен, возвращает понятную ошибку подключения, а не пустой список.

Определений инструментов в клиенте нет. Файл `client/contracts.js` удаляется.

## 5. Протокол между клиентом и сайтом

Запрос: `POST`, `Content-Type: application/json`, токен в заголовке `X-MCP-Token`.
`Authorization: Bearer <токен>` тоже принимается, но основным остаётся `X-MCP-Token`: часть
хостингов не передаёт заголовок `Authorization` в PHP.

```json
{ "v": 2, "action": "update", "args": { "kind": "chunk", "id": 12, "fields": {} },
  "request_id": "…", "session_id": "…" }
```

Ответ:

```json
{ "ok": true,
  "result": {},
  "meta": { "request_id": "…", "changeset_id": 481, "manifest": "<хеш>",
            "warnings": [], "new_log_errors": 0 } }
```

Ошибка: `{ "ok": false, "error": { "code": "revision_conflict", "message": "…", "details": {} }, "meta": {} }`.

Коды ошибок фиксированы и перечислены в манифесте: `unauthorized`, `forbidden_scope`,
`validation_failed`, `not_found`, `revision_conflict`, `lint_failed`, `undo_conflict`,
`not_reversible`, `request_state_error`, `response_too_large`, `internal_error` и т. д.

Из 1.10 переносятся без изменения смысла: проверка HTTPS и доверенных прокси, список
разрешённых IP, лимиты размера запроса и ответа, буферизация постороннего вывода PHP,
хранилище запросов и повтор ответа по `request_id`. Устаревшие поля верхнего уровня
(`type`, `name`, `content`, `id`) убираются.

`GET` по-прежнему отдаёт только название компонента, версию и признак включённости.

## 6. Токены и области доступа

Один токен в настройке `modxmcp.api_token` заменяется таблицей токенов.

Таблица `modxmcp_tokens`: `id`, `label`, `prefix` (первые символы для показа), `hash`
(SHA-256 токена; сам токен не хранится), `scope`, `plan_only`, `denied_groups`,
`expires_at`, `last_used_at`, `created_by`, `created_at`, `revoked_at`.

| Область | Разрешено |
|---|---|
| `read` | Все инструменты без записи, кроме `query_db` |
| `content` | + ресурсы, значения TV, файлы в источниках файлов |
| `develop` | + элементы, настройки, код, `run`, `query_db`, интеграции |
| `admin` | + пользователи и доступ, пакеты, `run_processor`, `maintenance` |

- Токен показывается один раз при создании в админке. Инструмента для выпуска токена нет:
  `regenerate_token` удаляется, чтобы токен не попадал в контекст модели.
- `plan_only`: все записи такого токена выполняются как пробный запуск (раздел 7.3).
- `denied_groups` задаётся для каждого токена. Общий выключатель групп для всего сайта —
  прежняя настройка `modxmcp.disabled_groups`.
- Действия по-прежнему выполняются от имени сервисного пользователя
  (`modxmcp.service_user_id`); что разрешено, определяет область токена.
- При обновлении с 1.x существующий токен из `modxmcp.api_token` переносится как токен
  `admin`, настройка очищается.

`run`, `query_db` и `run_processor` дополнительно требуют включённой настройки сайта
(`allow_run`, `allow_query_db`, `allow_run_processor`); по умолчанию все три выключены.

## 7. Единый контракт записи

Каждый инструмент-запись принимает общие аргументы и возвращает общий результат.

Аргументы: `expected_revision` (необязательно), `dry_run` (необязательно), `_request_id`
(необязательно).

Результат:

```json
{ "kind": "chunk", "id": 12, "revision": "<sha256>", "changeset_id": 481,
  "reversible": true, "changed": ["snippet"], "warnings": [] }
```

### 7.1. Ревизия

Ревизия объекта — SHA-256 от его канонического снимка (раздел 8.2): поля, связи и, для
статических элементов, содержимое файла. Она одна и та же в `get`, в результатах записи и
в журнале. Если передан `expected_revision` и он не совпадает с текущей ревизией, запись
отклоняется с `revision_conflict`, в `details` — текущая ревизия и список изменившихся полей.

### 7.2. Конвейер

1. Проверка области токена и группы.
2. Проверка аргументов по схеме вида.
3. Блокировка объекта (по объекту и, для статических элементов, по файлу).
4. Чтение текущего состояния, сверка `expected_revision`; проверка, не открыт ли объект
   на редактирование в админке (раздел 8.10).
5. Проверка кода (раздел 9.1) — для сниппетов, плагинов и файлов `.php`.
6. Снимок «до» в журнал.
7. Выполнение: штатный процессор MODX там, где он есть; транзакция БД; запись статических
   файлов через промежуточную копию с восстановлением при сбое (перенос из 1.10).
8. Снимок «после», вычисление ревизии, фиксация набора изменений.
9. Обновление кэша (отложенное для пакетных операций — перенос из 1.10).
10. Запись аудита.
11. Подсчёт новых строк журнала ошибок за время запроса → `meta.new_log_errors`.

При сбое на шагах 7–8 набор изменений помечается `failed`, а уже сделанные в нём изменения
откатываются по снимкам «до».

### 7.3. Пробный запуск

`dry_run: true` выполняет шаги 1–5 и возвращает, что было бы изменено: список объектов,
изменяемые поля, результат проверки кода, обратимость. Ничего не записывается, набор
изменений не создаётся. Для токена с `plan_only` пробный запуск включён принудительно, а в
результате стоит `planned: true`.

## 8. Журнал изменений и откат

Журнал не зависит от VersionX и работает для всех видов объектов.

### 8.1. Таблицы

`modxmcp_changesets` — набор изменений (один вызов записи):
`id`, `created_at`, `source` (`mcp` | `manager` | `external`), `token_id` (для `mcp`),
`user_id` (пользователь админки для `manager`), `session_id`, `request_id`, `tool`,
`summary`, `status` (`committed` | `failed` | `undone`), `reversible`, `undo_of` (id набора,
который этот набор откатывает), `checkpoint_id`.

`modxmcp_changes` — изменение одного объекта в наборе:
`id`, `changeset_id`, `seq`, `kind`, `object_key` (id или составной ключ), `label`
(имя объекта на момент изменения), `op` (`create` | `update` | `delete`),
`before`, `after` (снимки или ссылки на содержимое), `before_revision`, `after_revision`,
`reversible`, `note`.

Хранятся оба снимка, «до» и «после». Снимок «после» одного изменения совпадает со снимком
«до» следующего, а одинаковое содержимое хранится один раз (раздел 8.2), так что цепочка
правок места почти не добавляет. Снимок «после» нужен, чтобы восстановить и показать
правку, сделанную в обход журнала (раздел 8.10).

`modxmcp_checkpoints`: `id`, `created_at`, `token_id`, `session_id`, `label`,
`last_changeset_id`.

Таблицы создаются резолвером при установке пакета. Это первые собственные таблицы компонента.

### 8.2. Снимок

Снимок — канонический JSON: сырые поля объекта в отсортированном порядке плюс связи,
которые вид объявил своими:

| Вид | Что входит в снимок помимо полей |
|---|---|
| `chunk`, `snippet`, `template`, `plugin` | Содержимое статического файла; привязки наборов свойств |
| `plugin` | События плагина |
| `tv` | Привязки к шаблонам, доступ по группам ресурсов |
| `resource` | Значения TV, группы ресурсов |
| `user` | Профиль, членство в группах |
| `access_policy` | Карта разрешений |
| файл | Содержимое файла, права |
| прочие | Только поля |

Строки длиннее порога и содержимое файлов хранятся отдельно, в
`core/modxmcp-data/history/`, с именем по SHA-256 содержимого: одинаковое содержимое
хранится один раз. В снимке остаётся ссылка. Каталог лежит рядом с `requests`, вне кэша
MODX и вне веб-корня компонента.

В выводе `history_diff` значения секретных полей (хеши паролей, настройки типа «пароль»,
токены) заменяются на `[скрыто]`; в самих снимках они сохраняются, иначе откат невозможен.

### 8.3. Что записывается

- Каждое изменение, идущее через конвейер записи, включая пакетные операции (один набор,
  много изменений) и сам откат.
- Не записываются чтения, пробные запуски, отклонённые запросы.
- Объект, затронутый несколько раз в одном наборе, записывается один раз: снимок «до» —
  от первого касания, ревизия «после» — от последнего.

### 8.4. Инструменты

- `history {source?, session?, kind?, object?, since?, limit}` — наборы изменений, новые
  сверху: id, время, источник и автор, инструмент, описание, число объектов, статус,
  обратимость.
- `history_diff {changeset_id, object?}` — по каждому объекту: операция, изменённые поля,
  построчное сравнение для кода.
- `checkpoint {label}` — контрольная точка; возвращает её id.
- `undo` — одно из: `{changeset_id}`, `{last: N}`, `{session: true}`, `{to_checkpoint: id}`.
  Без `confirm: true` возвращает только план отката: какие объекты в какое состояние
  вернутся и где есть конфликты. С `confirm: true` выполняет.

### 8.5. Алгоритм отката

1. Собрать список наборов, отсортировать от новых к старым; внутри набора идти по `seq`
   в обратном порядке.
2. Для каждого изменения сверить текущую ревизию объекта с `after_revision`.
3. Применить обратную операцию:
   - `update` → вернуть поля и связи из снимка «до»;
   - `create` → удалить объект (ресурс — в корзину);
   - `delete` → восстановить из снимка **с прежним id**; для ресурса, удалённого в
     корзину, — снять признак удаления.
4. Весь откат — один новый набор изменений с `undo_of`. Откат этого набора возвращает
   состояние обратно («повтор»).
5. Исходные наборы получают статус `undone`.

Восстановление выполняется напрямую через объекты xPDO, а не через процессоры: штатные
процессоры не умеют создавать объект с заданным id и не восстанавливают связи как единое
целое. После отката обновляется кэш. События сохранения MODX при откате вызываются для
элементов и ресурсов, чтобы сторонние плагины (в том числе VersionX) увидели изменение.

### 8.6. Конфликты

Если текущая ревизия объекта не равна `after_revision`, объект меняли после этого набора —
в админке, в обход журнала или более поздним вызовом MCP, который в откат не включён. Тогда:

- план отката помечает объект как конфликтный, показывает расхождение и называет более
  поздние наборы, изменившие объект, с их авторами;
- откат с `confirm: true` останавливается до каких-либо изменений с ошибкой `undo_conflict`;
- `force: true` разрешает откат поверх чужих правок; при этом текущее состояние сохраняется
  как снимок «до» нового набора, так что и это можно отменить.

Следствие: откатить набор «из середины» можно только если более поздние изменения тех же
объектов тоже входят в откат либо указан `force`.

### 8.7. Необратимое

`reversible: false` объявляется в манифесте и повторяется в результате вызова:

- установка и удаление пакетов;
- `maintenance`: очистка корзины (остальные операции не меняют данные);
- `run_processor`, `run` — их побочные эффекты неизвестны;
- изменения файла больше `modxmcp.history_max_blob_bytes` — запись выполняется, но в
  `warnings` сообщается, что откат этого изменения невозможен;
- побочные изменения, сделанные сторонними плагинами и процессорами внутри вызова
  (например, пересчёт URI дочерних ресурсов), журнал не видит.

### 8.8. Хранение

Настройки: `modxmcp.history_retention_days` (по умолчанию 30),
`modxmcp.history_max_bytes` (по умолчанию 200 МБ), `modxmcp.history_max_blob_bytes`
(по умолчанию 5 МБ). Очистка выполняется при записи, не чаще раза в час: удаляются самые
старые наборы и содержимое, на которое больше нет ссылок.

### 8.9. Страница «История» в админке

Список наборов с фильтрами по источнику, автору, токену, сессии, виду и объекту; просмотр
сравнения; кнопки «Откатить набор» и «Откатить до точки» с тем же планом и подтверждением,
что и в инструменте `undo`. Требует права `settings`, как остальные страницы компонента.

### 8.10. Правки людей в админке и в обход журнала

Сайт одновременно правят ИИ через MCP и люди через админку (а статические файлы — ещё и
через редактор или FTP). Журнал учитывает все три источника.

**Запись правок из админки.** Плагин компонента подписан на события MODX «перед
сохранением» и «после сохранения / удаления». На событии «перед» он берёт снимок «до», на
событии «после» — снимок «после» и создаёт набор изменений с `source: manager` и
`user_id` автора. Такой набор виден в `history` и откатывается теми же средствами, что и
набор MCP, — из инструмента `undo` или кнопкой на странице «История».

Покрытие определяется тем, какие события есть в MODX 2.8:

| Вид | Запись из админки |
|---|---|
| Ресурсы (включая значения TV), чанки, сниппеты, шаблоны, плагины, TV, пользователи | Полная: события «перед» и «после» есть |
| Файлы в источниках файлов | Частичная: события есть не для всех операций; что именно покрывается, уточняется на этапе 3 |
| Системные настройки, права доступа, контексты и прочее | Событий сохранения нет — правка обнаруживается как внешняя (ниже) |

Вызовы MCP идут через те же процессоры и вызывают те же события. Конвейер записи на время
своего вызова ставит признак, по которому плагин пропускает событие, — двойной записи нет.

Запись из админки включается настройкой `modxmcp.history_track_manager` (по умолчанию
включена).

**Правки в обход журнала.** Изменение, для которого нет события (настройки, статический
файл через FTP, прямой запрос в базу), журнал в момент правки не видит. Оно обнаруживается
при следующем обращении MCP к объекту: текущая ревизия не совпадает с `after_revision`
последней записи журнала об этом объекте. Тогда создаётся набор с `source: external`:
снимок «до» берётся из `after` последней записи, снимок «после» — текущее состояние. Автор
и точное время неизвестны, это отмечается в наборе. Дальше с ним можно работать как с
любым другим: посмотреть сравнение, откатить.

**Как ИИ узнаёт о чужих правках.**

- Клиент запоминает ревизии объектов, прочитанных и изменённых в сессии, и подставляет
  `expected_revision` сам. Если человек успел поправить объект после того, как модель его
  прочитала, запись отклоняется с `revision_conflict`. В `details` — кто и когда изменил
  объект (из журнала) и какие поля. Модель перечитывает объект и вносит свою правку поверх
  актуального состояния.
- `history {source: "manager", since}` отвечает на вопрос «что люди меняли с такого-то
  момента». `site_info` показывает число ручных правок с последней сессии этого токена.

**Объект открыт в админке.** Когда человек открывает ресурс или элемент на редактирование,
MODX ставит блокировку. Конвейер записи проверяет её: если объект сейчас редактирует другой
пользователь, запись отклоняется с ошибкой `locked` и именем пользователя. Иначе человек,
нажав «Сохранить», затёр бы правку ИИ целиком, не заметив её. `force: true` разрешает
запись несмотря на блокировку.

**Чего это не даёт.** Автоматического слияния правок нет: при конфликте решает модель или
человек. Журнал не предупреждает человека в админке о том, что ИИ изменил объект, пока
форма была открыта, — MODX такой возможности не даёт; последствия видны и исправимы на
странице «История».

## 9. Проверка результата

### 9.1. Проверка PHP до сохранения

Код сниппета, плагина или файла `.php` разбирается через `token_get_all` с флагом
`TOKEN_PARSE`. При синтаксической ошибке запись отклоняется с `lint_failed`, в `details` —
сообщение и номер строки. Код не выполняется.

Ограничения: проверяется синтаксис для версии PHP сервера; ошибки времени выполнения и
часть ошибок компиляции (например, повторное объявление функции) так не ловятся.
`skip_lint: true` позволяет сохранить намеренно неполный код; факт пропуска пишется в журнал.

### 9.2. `run`

Выполнить сниппет с параметрами или отрендерить чанк либо строку с тегами MODX в заданном
контексте и для заданного ресурса. Возвращает вывод (с лимитом длины), время выполнения и
новые строки журнала ошибок. Требует `allow_run` и области `develop`. Не обратим: сниппет
может менять данные сам.

### 9.3. `check_page`

Запрашивает страницу сайта по id ресурса или пути и возвращает: HTTP-статус, время ответа,
размер, заголовок страницы, неразобранные теги `[[…]]` в выводе, новые строки журнала
ошибок за время запроса. Адрес обязан принадлежать одному из контекстов этого сайта;
произвольные внешние адреса запрещены.

### 9.4. `audit_site`

Возвращает список проблем с указанием объекта: ссылки `[[~id]]` на несуществующие ресурсы;
вызовы несуществующих чанков и сниппетов; неиспользуемые чанки, сниппеты и TV; статические
элементы с отсутствующим файлом; дубли алиасов в одном родителе; сниппеты и плагины, не
проходящие проверку PHP. Параметр `checks` ограничивает набор проверок. Использует индекс
графа зависимостей из 1.10.

## 10. Черновики ресурсов (второй этап)

`invoke {kind: "resource", op: "create_draft", id}` создаёт неопубликованную скрытую копию
ресурса и возвращает ссылку предпросмотра. Правки ведутся в копии. `apply_draft` переносит
содержимое и значения TV из копии в оригинал одним набором изменений и удаляет копию;
`discard_draft` удаляет копию. Связь копии с оригиналом хранится в таблице компонента.

## 11. Экономия контекста

- `list`: параметр `fields`; по умолчанию короткий набор полей вида; `limit` 50; в ответе
  `total` и `next_start`.
- `get`: параметр `fields`; длинный код по умолчанию обрезается с указанием полного размера
  и подсказкой использовать `view_code`.
- Текстовая часть ответа MCP — компактный JSON без отступов.
- Описания инструментов короткие; подробности — в `describe` и справке.
- Справка отдаётся как ресурсы MCP; `help` остаётся для клиентов без их поддержки.
- Сценарии (prompts): «изучить сайт», «создать тип страницы», «провести аудит».

  miniShop2 и MIGX) — возможности остаются через виды.

- Поля верхнего уровня запроса `type`, `name`, `content`, `id`.
- `client/contracts.js` и определения инструментов в `client/index.js`.

## 15. Этапы

Каждый этап заканчивается вашей проверкой на стенде разработки компонента.

1. **Ядро** (сделано). Структура `src/`, автозагрузка, протокол v2, манифест, токены с
   областями, тонкий клиент, `capabilities`, `site_info`, `describe`, `help`,
   `request_status`; минимальное управление токенами на странице компонента.
2. **Запись и журнал** (сделано, кроме перечисленного ниже). Конвейер записи, ревизии,
   таблицы журнала, хранилище содержимого, проверка PHP, обнаружение внешних правок.
   Осталось: плагин записи правок из админки, проверка блокировки в админке, `duplicate`,
   `invoke` с `make_static` и авто-статикой, очистка журнала по сроку и объёму. Виды `chunk`, `snippet`, `template`, `plugin`, `tv`, `category`.
   Инструменты объектов и кода, `history`, `history_diff`, `undo`, `checkpoint`.
3. **Контент и файлы** (ресурсы сделаны; файлы и `media_source` — в работе). Вид `resource` с TV, `resource_tree`, `bulk_resources`, файловые
   инструменты, `media_source`.
4. **Проверка.** `run`, `check_page`, `read_log`, `audit_site`, `search`, `replace`,
   `find_usages`, `dependency_graph`.
5. **Администрирование.** Виды настроек, доступа, пакетов; `install_package`,

## 16. Открытые вопросы

1. **Откат до контрольной точки.** Откатывать только изменения MCP после точки
   (предложение; ручные правки людей остаются и при пересечении дают конфликт) или все
   изменения, включая сделанные в админке?
2. **Срок и объём истории.** Подходят ли 30 дней и 200 МБ по умолчанию? С записью правок
   из админки журнал растёт быстрее.
3. **`run`.** Нужен ли инструмент выполнения сниппетов на боевом сайте вообще, или
   достаточно `check_page`?
4. **Области доступа.** Достаточно ли четырёх уровней, или нужен ручной выбор групп для
   каждого токена сверх `denied_groups`?
5. **Блокировка в админке.** Отклонять запись ИИ, если объект открыт у человека
   (предложение), или только предупреждать?
